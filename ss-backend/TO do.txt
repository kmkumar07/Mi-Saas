// Cache entitlements in RAM for 5 minutes
const entitlementCache = new Map();

async function fetchEntitlements(tenantId, customerId) {
  const key = `${tenantId}:${customerId}`;
  
  if (entitlementCache.has(key)) {
    const { expires, data } = entitlementCache.get(key);
    if (Date.now() < expires) return data;
  }

  const res = await fetch(`${process.env.MINI_SAAS_URL}/entitlements/${tenantId}/${customerId}`, {
    headers: {
      "x-api-key": process.env.MINI_SAAS_KEY,
      "x-tenant-id": tenantId
    }
  });

  const data = await res.json();
  entitlementCache.set(key, {
    expires: Date.now() + 5 * 60 * 1000,
    data
  });

  return data;
}

# Layered Permission Model Implementation

## Architecture Overview

The permission model follows a strict hierarchy where every layer builds on the previous:

```
Identity (global human)
  └─ Organization Member (baseline, required)
       ├─ RBAC roles (dynamic, feature-based)
       ├─ Organization Admin (tenant governance)
       └─ Product Access (scope control)
```

**Core Principle**: No layer bypasses Organization Member. All authorization checks must verify membership first.

## Database Schema Changes

### New Tables in UAM Schema

1. **`identities`** - Global human identity

   - `id` (uuid, PK)
   - `email` (varchar, unique) - normalized email for identity matching
   - `firstName`, `lastName` (optional profile fields)
   - `createdAt`, `updatedAt`

2. **`auth_accounts`** - Login methods per identity

   - `id` (uuid, PK)
   - `identityId` (uuid, FK → identities)
   - `provider` (enum: 'local', 'azure_ad', 'google', 'cognito')
   - `providerAccountId` (varchar) - external provider ID
   - `email` (varchar) - may differ from identity.email for provider-specific emails
   - `passwordHash` (varchar, nullable) - only for local provider
   - `externalId` (varchar, nullable) - Azure AD Object ID, etc.
   - `isActive`, `isEmailVerified`
   - `lastLoginAt`, `createdAt`, `updatedAt`
   - Unique constraint: (identityId, provider, providerAccountId)

3. **`organization_members`** - Baseline membership (identity ↔ tenant)

   - `id` (uuid, PK) - **This becomes the JWT `sub` claim**
   - `identityId` (uuid, FK → identities)
   - `tenantId` (uuid, FK → subscription.tenants)
   - `isActive` (boolean)
   - `joinedAt`, `createdAt`, `updatedAt`
   - Unique constraint: (identityId, tenantId)

4. **`organization_admins`** - Tenant-level administrative authority

   - `id` (uuid, PK)
   - `organizationMemberId` (uuid, FK → organization_members, cascade delete)
   - `tenantId` (uuid, FK → subscription.tenants) - denormalized for queries
   - `grantedBy` (uuid, FK → organization_members, nullable)
   - `grantedAt`, `createdAt`
   - Unique constraint: (organizationMemberId) - one admin record per member
   - **Note**: Must also exist in organization_members (enforced by FK)

5. **`product_access_permissions`** - Product-level access control

   - `id` (uuid, PK)
   - `organizationMemberId` (uuid, FK → organization_members, cascade delete)
   - `productId` (uuid, FK → subscription.products)
   - `tenantId` (uuid, FK → subscription.tenants) - denormalized for queries
   - `grantedBy` (uuid, FK → organization_members, nullable)
   - `grantedAt`, `createdAt`
   - Unique constraint: (organizationMemberId, productId)

### Schema Modifications

- **Remove from `uam.users`**: `accountType`, `organizationId`, `isCompanyOwner` (billing-only fields)
- **Keep in `uam.users` temporarily**: For migration reference, then drop after data migration
- **`ss-backend.accounts.accountType`**: Remains the ONLY source of truth for billing

### RBAC Tables (Unchanged)

- `uam.roles` - System and tenant roles
- `uam.user_roles` - **Update**: Change `userId` → `organizationMemberId`
- `uam.role_permissions` - Role-to-feature permissions
- `uam.product_invlovemnet_roles` - Product-role mappings

## Authorization Flow

### Authentication Resolution

```
auth_account (login) 
  → identity (global person)
    → organization_members (tenant membership)
      → JWT issued with sub = organization_members.id
```

### Authorization Check Flow

All resource access must follow this sequence:

1. **Extract JWT `sub`** → `organizationMemberId`
2. **Verify Organization Membership**:
   ```typescript
   const member = await orgMemberRepo.findById(organizationMemberId);
   if (!member || !member.isActive || member.tenantId !== requestedTenantId) {
     throw ForbiddenException('Not a member of this organization');
   }
   ```

3. **Check Product Access** (if accessing product-scoped resource):
   ```typescript
   const hasAccess = await productAccessRepo.exists({
     organizationMemberId,
     productId,
     tenantId
   });
   if (!hasAccess) {
     throw ForbiddenException('No access to this product');
   }
   ```

4. **Check Organization Admin** (if performing admin action):
   ```typescript
   const isAdmin = await orgAdminRepo.exists({ organizationMemberId, tenantId });
   // Admin status grants tenant governance, but does NOT bypass RBAC
   ```

5. **Check RBAC** (always required for feature access):
   ```typescript
   // Existing RBAC logic unchanged
   // RBAC subject = organization_members.id (not identity.id)
   const hasPermission = await rbacService.checkPermission(
     organizationMemberId, // subject
     featureKey,
     action
   );
   ```


### Key Authorization Rules

- **Organization Member is mandatory**: No access without active membership
- **Product Access is additive**: Grants scope, but RBAC still applies
- **Organization Admin is additive**: Grants tenant governance, but RBAC still applies
- **RBAC is never bypassed**: Even admins must have RBAC permissions for features

## Migration Strategy

Since this is a greenfield reset:

1. **Drop existing `uam.users` table** (after extracting any needed reference data)
2. **Create new tables** in order: identities → auth_accounts → organization_members → organization_admins → product_access_permissions
3. **Update `user_roles`** table: Rename `userId` column to `organizationMemberId`, update FK
4. **Update all code references** from `userId` to `organizationMemberId` where appropriate

## Critical Implementation Notes

1. **JWT Structure**: `sub` = `organization_members.id` (tenant-scoped), includes `tenantId` claim
2. **No Bypass Logic**: Every authorization check starts with membership verification
3. **Account Type**: Only exists in `ss-backend.accounts.accountType`, never inferred
4. **RBAC Subject**: Always `organization_members.id`, never `identity.id`
5. **Cascade Deletes**: Removing organization_member cascades to admins, product access, and user_roles
6. **Comments**: Add extensive comments explaining why each layer cannot bypass the previous
